  What stands out from the log: every layer that was tested — clock
  sharing/independence, the master/slave timing-engine gate, DSC slice config,
  dual- vs single-pipe topology, cont-splash gates, PHY enable sequencing — sits
  above or alongside one thing nobody looked at: bus/memory-bandwidth voting 
  for the display path. I checked, and this driver fork genuinely has that
  subsystem (sde_core_perf.c, sde_power_handle.c), it's distinct from everything
  already ruled out, and it would specifically produce exactly the symptom
  pattern you're seeing — FIFO underflow — because an underfed command/video
  FIFO is the textbook signature of insufficient DDR bus QoS for the DSI path,
  not a clock, encoder, or PHY problem.

  Two things make this a better fit than "PHY analog/power-sequencing" as the
  leading theory:
  - It explains why SINGLEPIPE_DSC with ctrl1 fully removed from the DT still 
    showed FIFO underflow and command-transfer failures on the one remaining 
    controller — bandwidth starvation doesn't care about topology, a
    power-sequencing issue would be a stranger fit for an isolated single link
    that was otherwise rock-solid every other time it ran alone.
  - It's a subsystem that depends on something Android's live session was
    already actively voting for (SurfaceFlinger keeps a steady-state bandwidth
    vote going) and that a kexec transition has no obvious reason to
    re-establish correctly — the same "stale state inherited across kexec" shape
    as the camera-clock, GENI, and ION issues already found and fixed in this
    project, just in a different subsystem nobody's checked yet.

  Concretely, sde_core_perf.c's _get_sde_client_type()
  (techpack/display/msm/sde/sde_core_perf.c:279-289) routes the bus vote either
  straight to ICC (RT_CLIENT) or through the SDE RSC hardware sequencer
  (RT_RSC_CLIENT/RT_RSC_PRIMARY_MODE) depending on perf->bw_vote_mode and
  perf->sde_rsc_available — and NOTES.md already logged SDE RSC probed
  successfully at boot, which (per the project's own repeated lesson this
  session) is a software-level success report, not proof the hardware
  sequencer's actual solver state survived the kexec transition correctly.

  This is checkable with zero rebuild/reboot risk, using the same debugfs-first
  method already used throughout this session:
  - /sys/kernel/debug/dri/0/core_perf/{bw_vote_mode,core_clk_rate,fix_core_ab_vo
    te,fix_core_ib_vote} — read before and during a held kms_atomic2 commit,
    same pattern as the clk_summary checks.

    status file at sde_rsc.c:1374) — read its reported solver state during the
    same held commit.
  - If bw_vote_mode shows DISP_RSC_PRIMARY_MODE/RSC path is active, that's the
    thread to pull: compare the vote values during a failing commit against what
    a真实 cold-boot Android session would show (if that's even recoverable via
